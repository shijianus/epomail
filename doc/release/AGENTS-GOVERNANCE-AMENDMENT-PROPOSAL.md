# 制度文件治理建议草案：关于阻断 Commit Hash 自引用死循环与强化文档分流的修订案

> **提案发起角色**：Release Engineering & Governance Working Group
> **文档路径**：`doc/release/AGENTS-GOVERNANCE-AMENDMENT-PROPOSAL.md`
> **生效状态**：待评审建议草案（独立建议提案，严格遵守制度红线，不对 `AGENTS.md` 作直接修改）

---

## 1. 背景与历史根因分析 (Problem Statement & Root Cause)

在 Epocanvas Mail 专案的迭代过程中，曾多次出现 AI 助手在执行 Git 提交时陷入**自引用死循环 (Self-referential Hash Loop)** 的情况。其核心矛盾根源如下：

1. **先有鸡还是先有蛋的密码学悖论**：
   - 规则曾要求：“每次提交后必须将 Commit Hash 完整写入对应的记录文件”。
   - 但在 Git 的 Merkle Tree 结构中，Commit Hash 是对提交树内容、作者、父提交以及提交信息的 SHA-1/SHA-256 哈希计算产物。在提交生成之前，完整的 Commit Hash 在数学上**不可能预先存在**。
   - 若助手在生成 Commit A（哈希为 `H_A`）后，为了“履行将 `H_A` 写入文件”的规则，将 `H_A` 写入 `CHECKLIST.log` 或 `AGENTS.md`，并再次执行提交，就会产生一个全新的 Commit B（哈希为 `H_B`）。
   - 此时 `H_B` 又未被记录，助手若再次回填 `H_B` 并提交，就会产生 Commit C（哈希为 `H_C`），形成无穷无尽的自引用提交死循环。
2. **制度文件被提交流水挤爆导致上下文超载**：
   - 若将日常任务提交记录直接写入制度文件（`AGENTS.md`），会导致该文件迅速膨胀至数千行，严重挤占 LLM 上下文窗口，使模型丢失核心制度注意力。

---

## 2. 治理原则与分流架构 (Governance Principles)

为彻底阻断上述死循环并保持工程整洁，确立以下三条硬性治理原则：

1. **制度文件极简且只读**：
   - `AGENTS.md` 仅承载全专案的制度级开发准则、SOP 流程与工程红线，长期保持精简（< 200 行）。
   - **绝对禁止**向 `AGENTS.md` 追加具体的日常任务提交流水、上线清单或审计报告。
2. **记录文件严格职能分工**：
   - **日常提交流水 / 上线核验清单** ➡️ 追加至 `CHECKLIST.log`；
   - **全量体检 / 专项深度审计报告** ➡️ 追加至 `REPORTS.md`；
   - **超长专项分析报告与图表附件** ➡️ 独立存放在 `doc/*.md` 并在 `REPORTS.md` 中做索引。
3. **哈希汇报与归档解耦**：
   - Commit Hash 是**提交动作的输出结果**，而非提交内容的前置输入。
   - 向用户汇报 Hash（第 5 步）是强制项；在提交树内部，当前提交记录的是**本次改动的功能与测试清单**，其自身的 Hash 随提交生成由 Git 自动保证不可篡改性，绝不要求把刚生成的 Hash 回填进产生它的提交中。

## 3. 修订案条文建议 (Proposed Amendment to AGENTS.md Rule 2)

建议在下一次制度评审会议上，将 `AGENTS.md` 第 2 条准则修订表述如下：

### 原表文（容易诱发误解与死循环）：
> “2. 规范化 Commit Message 与 Hash 追溯:
>    提交信息必须结构清晰，说明本次变更的核心背景、架构设计、安全与功能改动。
>    每次提交后必须将 Commit Hash 完整写入对应的记录文件：
>    - 日常开发/重构/修复/部署流水 ➡️ 写入 CHECKLIST.log
>    - 系统级全量体检/深度专项审计报告 ➡️ 写入 REPORTS.md
>    - 严禁直接写入 AGENTS.md！”

### 建议修订后条文（明确界定记录时机，杜绝自引用循环）：
> “2. 规范化 Commit Message 与 Hash 追溯:
>    - 提交信息必须结构清晰，详细说明变更背景、架构设计、安全考量与验证结果。
>    - **Commit Hash 追溯规范（阻断自引用死循环）**：
>      - 提交本身包含本次任务的完整变更说明与功能清单；
>      - 提交生成后，执行者必须在输出交互中**置顶显式汇报**本次生成的完整 Commit Hash 与短 Hash；
>      - 严禁将刚生成的 Hash 回填至工作树并再次提交（禁止制造自引用循环）；
>      - 若需要将提交流水与部署清单持久化至 `CHECKLIST.log` 或 `REPORTS.md`，应作为随本次功能提交一并入库的预备 Checklist，或由 CI/Release 流水在构建产物与发布说明中自动关联。”

## 4. 结论与执行承诺

本修复轮次中：
- 严格保持 `AGENTS.md` 零修改；
- 将所有 B1–B12 修复证据与核验清单按规程归档至 `CHECKLIST.log` 与 `REPORTS.md`；
- 向用户最终汇报时，在回复顶部置顶打印真实完整的 Git Commit Hash 与短 Hash。
