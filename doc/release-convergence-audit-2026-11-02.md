## 5. 账号恢复与持久状态

### A1. P1：MFA 恢复流程没有闭合

- **首次 Passkey**：`mail-worker/src/service/totp-service.js:263-285` 激活第一把 Passkey 并启用 MFA，但不生成恢复码；父提交中该路径曾生成。TOTP 启用 `:192-208` 才生成，单独重新生成 `:233-239` 又要求既有因子证明。
- **准确影响范围**：普通密码／已绑定 OAuth 加唯一 Passkey 作为 MFA、未额外保存恢复码的用户，在该设备丢失后不能自行建立替代因子；不是说系统支持无密码登录，也不是说管理员不能处理。
- **最后一枚恢复码**：登录消费该码后，后续重新生成恢复码或替换因子仍要求另一份现有因子证明，缺少受限的恢复完成通道。管理员重置仍是可用兜底。
- **最小修复**：首次激活时与状态变更一并持久化恢复码，安全展示并要求确认保存；恢复登录后签发短时、一次性、绑定用户／会话／认证版本和用途的恢复授权，只允许重新配置／轮换因子，不降低普通二次验证要求。
- **正常验收**：第一把 Passkey 的恢复材料可保存；合法使用最后一枚恢复码后能完成因子轮换并得到新恢复材料；常规管理和管理员恢复保持可用。

### A2. P1／失败分支：OAuth 首次密码资格仅依赖可丢失的 KV 标记

- **证据**：`oauth-service.js:1017-1030` 在绑定已提交后写 `INITIAL_PASSWORD`，失败只记录日志；`user-service.js:616-626` 没有该标记即拒绝首次设密。普通改密要求用户并不知道的随机旧密码，后续提供方登录也不会补足持久密码来源状态。
- **影响**：账号本身及 OAuth 登录可以存在，但“设置首个密码”长期不可用，形成对外部提供方的不必要依赖。
- **最小修复**：将密码来源／首次设密状态放入 D1，与建号或绑定一致提交；保留最近提供方认证、当前会话和 CAS 校验。旧账号只能依据可信迁移证据补状态，不能仅凭“有 OAuth 绑定”就允许改密。
- **正常验收**：合法 OAuth 建号、再次登录、设置首个密码与后续改密的状态一致，临时缓存缺失不永久丢失功能。

### A3. P1／委派场景：邀请码发放没有统一角色授予边界

- **证据**：`security/security.js:125` 将创建邀请码映射为 `reg-key:add`；`reg-key-service.js:13-42` 收到调用者 ID，但只检查目标角色存在即保存；`login-service.js:313-325,364-387` 建号使用该角色。已有 `rbac-guard-service.js:73-87` 的角色授予守卫未接入此路径。
- **准确边界**：前提是非站长被委派邀请码创建能力；不是普通用户均能操作，也未核实线上角色委派。这里需要的是防御性授权一致性修复，不需要通过构造提权请求证明。
- **最小修复**：创建和兑换均使用统一角色授予规则；保留邀请码可选／必需模式、原子扣减和失败回补。
- **完成条件**：所有产生用户角色的写入入口均有一致的授权审阅；正常普通角色邀请与兑换不退步。

### A4. P1／OIDC 能力：ID Token 验签和 nonce 契约不兼容标准客户端

- **证据**：`oauth-provider-service.js:314-319,357-369` 宣告 HS256 并用通用 JWT 工具签 ID Token；`utils/jwt-utils.js:15-25,45-53` 使用站点 JWT 密钥，而 `oauth-app-service.js:200-205` 给每个应用生成独立 client secret。授权数据没有贯穿保存、返回 nonce。
- **影响**：按标准客户端密钥配置 HS256 验签或要求 nonce 的 OIDC 接入不能完整完成；仅调用 UserInfo 的定制客户端可能仍工作。不能据定制接入成功宣称标准 OIDC 已验收。
- **最小修复**：将 OIDC 签名与站点会话密钥隔离；选定明确可验证的客户端签名契约，推荐非对称签名、kid／JWKS 和 issuer 生命周期，并贯穿 nonce。只在相应 scope 下签发所需身份数据。绝不向客户端分发站点 JWT 密钥。
- **正常验收**：以合成密钥和标准客户端对正常签发的 Discovery、issuer、audience、nonce 和签名做互操作核对；无需接触生产凭据。

### A5. P1：应用停用、授权撤销与重新授权缺少统一持久代际

- **证据**：`oauth-app-service.js:302-315` 停用只改应用状态，`oauth-provider-service.js:330-354` 的 UserInfo 检查用户和 grant，却不检查应用状态。`oauth-app-service.js:345-371,465-528` 撤销／重新授权没有授权版本；`oauth-provider-service.js:203-208` 记录 grant 失败仍继续返回授权码。
- **影响**：产品中的“停用应用”和“撤销授权”无法完全表达后端消费语义，重新授权也不能明确区分授权前后的不同阶段；关键持久化失败可能在界面显示成功后才暴露。
- **最小修复**：应用有效状态、grant 状态／版本进入每次消费的权威条件；grant 与授权码在同库提交边界内形成一致事实，不能吞掉关键失败。保留授权列表、停用、恢复与重新授权功能。
- **完成条件**：静态核对状态和版本的生成、保存、消费链一致；正常授权／主动撤销／重新授权的用户结果、记录及版本相符，不以旧令牌重放或利用验证作为本轮方法。

### A6. P1／基础设施失败分支：建号、主邮箱和 OAuth 关联仍可能半提交

- **证据**：`user-service.js:1352-1364` 管理建号依次写 user、资料、account；`login-service.js:246-270,313-336` 注册虽有补偿，但清理失败缺少持久恢复任务。`oauth-service.js:989-1052` 绑定明确失败有补偿，结果不明异常仍会走 release；`utils/oauth-bind-claim.js:169-175` 释放可删除恢复线索。
- **影响**：正常基础设施异常或进程中断后，可能留下没有主邮箱／没有完成关联的账号，重试又受唯一邮箱和邀请码状态阻挡。
- **最小修复**：当前同库把核心写入纳入 D1 batch；保留双库接口，但以持久 provisioning 状态和幂等补偿任务收敛跨库流程。结果确认或补偿完成前保留恢复线索，不能对结果未知的成功写入盲目删用户。
- **完成条件**：静态审阅提交与补偿边界，正常创建、重复确认和已有恢复记录的处理能取得一致最终状态；不以安全崩溃或触发脚本作为验收要求。

### A7. P2：逐会话状态和角色配置的原子性仍可改善

- `login-service.js:661-706,910-966` 及 `security/security.js:238-244` 对用户的 KV 会话整包读改写；正常多设备更新有覆盖其他会话变更的结构性风险。认证版本已解决敏感变更撤销，不重复报告旧问题。建议逐步将单会话状态、过期和设备期限放入独立 D1 记录，KV 只缓存；不能以任何退出都注销全部设备替代单会话功能。
- `role-service.js:393-459` 的角色属性、权限关系、用户迁移和默认角色切换分步提交；`init/init.js:1756-1760` 缺少角色／权限联合唯一约束，`:1027-1043` 的 INSERT OR IGNORE 不能单独保证关系不重复。建议同库 batch 和经规范化后的联合唯一约束；保留用户删除过的角色、自定义角色与稳定默认组。
- 上述是静态结构性问题，本轮未复现并发时序。正常多设备分别退出、角色配置与重复初始化应作为对应修复的行为核对。

### A8. P1／旧库升级准入：关键唯一索引迁移缺少最终约束检查

- **证据**：`init/init.js:1487-1494` 先删除旧邮箱索引，再建立 NOCASE 唯一索引，失败仅 warning；原始 user／account 表定义 `:1862-1895` 不能替代该唯一约束。历史重复资料或建立索引失败时，必须明确指出未满足的关键不变量。
- **最小修复**：先做只读数据／索引检查，新约束建立成功前不丢旧保护；迁移后确认关键表、列、索引和版本，未满足则不报告完整升级成功。历史重复资料保留待处理记录，不自动粗暴删除。
- **排除误报**：OAuth claim／单次凭证在后续迁移函数中虽有 catch，完整 init 的 `intDB` 已先无 catch 建同表／索引，不能仅凭后续 warning 报“缺表仍成功”。六标准角色播种失败传播与完成标记也已在本基线修复。重复幂等版本调用本身不是上线阻塞。

## 6. 邮件与存储的一致性

### M1. P1：普通外发 UNKNOWN 尚无可完成的对账流程

- **证据**：`email-service.js:1085-1132` 在供应商结果不明、或已接受但本地写回失败时进入 UNKNOWN；接受 ID 仅在成功 batch 中持久化。`mail-outbound-service.js:56-63,122-150` 阻止重复派发、过期 PREPARED 和补偿 FAILED，但不将 UNKNOWN 对账为最终状态。`resend-service.js:155-182` 的任务关联恢复针对 notification_outbox，不是普通 mail_outbound_task。
- **影响**：正常网络或持久化异常后，实际已发邮件可能长期显示处理中，配额也被占用。用户另开请求发送会增加重复投递可能。
- **最小修复**：供应商稳定任务关联、接受事实持久化、回执／查询对账及可审计人工处理入口；归档和配额按确认事实完成。
- **保全**：现有幂等键、发送租约、先归档与次数预留正确；**UNKNOWN 不得简单超时重发或随意释放配额**。
- **正常验收**：供应商记录、任务、归档和计数能对应同一封邮件；同幂等键查询／重试不产生第二次投递。

### M2. P1：管理员删除仍绕过新生命周期原语

- **证据**：`all-email-api.js:10-17` 调旧 `physicsDelete/batchDelete`；`email-service.js:1973-1978,2436-2447` 分别删附件、星标和邮件，批删最终又按动态条件删除。`star-service.js:107-108` 对全部 ID 构造单一 IN，没有分片。附件删除前一步已提交并可能清理对象。
- **影响**：正常大批清理可能在部分数据已删除后中断；并发新邮件可能进入最终删除集合，却不在先前附件清理集合。管理员物理删别名同样需要核对。
- **最小修复**：复用固定 ID 快照、有界分批的生命周期事务，邮件／星标／附件元数据／对象删除义务一起提交；保留无主件与管理员权限场景，并对在途发送明确暂缓。
- **正常验收**：合法大批数据分批收敛，结果数量及剩余引用一致；不因部分完成造成正文仍在而附件消失。

### M3. P1：转发副作用无持久任务，fallback 缺附件与 CID

- **证据**：`email/email.js:317-326` 已标记入站 COMPLETE，`:333-470` 才做转发／TG；完成态重复进入直接返回。`:449-459` 的个人转发 fallback 只传主题、正文和地址，不携附件／CID，失败主要日志记录。
- **最小修复**：入站完成时同时记录每个目标的独立后续任务和稳定键；传递完整附件与 CID 映射。结果不明同样不得盲目重发。
- **保全**：原生无损转发优先、本地副本、all／alias 范围、次数规则、循环保护和模式限制保留；未实现的 rules 与“不留副本”继续明确拒绝。
- **正常验收**：合法包含普通附件和内嵌图的邮件，fallback 仍完整；目标互不阻塞，有可查询的最终结果。

### M4. P1／管理操作：改存储位置或全局关 BYO 改变旧对象定位

- **证据**：`setting-service.js:490-508,625-627,710-737` 可改系统桶／endpoint／BYO 开关；`r2-service.js:22-95,127-178` 按当前配置解析旧对象，读取与 forDeletion 对 BYO 开关的处理不同。附件、raw 恢复及删除队列没有完整历史后端定位。
- **影响**：正常管理员保存配置后，旧附件／恢复 MIME 可能不可读，或旧桶清理义务失去定位。
- **最小修复**：有存量对象、raw 或待删除任务时，阻止改变其存储位置；关闭 BYO 只停止新增使用，不切断旧数据读取／清理。后续再做存储版本定位和受控迁移。
- **保全**：已有个人换桶保护继续保留，不为了上线移除 BYO。
- **正常验收**：正常配置更新不改变历史对象可读性，位置变更有明确阻止或迁移结果，清理能指向原存储。

### M5. P1：加密邮件的主题／正文搜索先在密文上过滤

- **证据**：`email-service.js:620-626,965-967` 加密主题／正文；`:189-224` 的 SQL LIKE 却直接使用这些列，`:241-250` 先查和计数，`:277-284` 后解密；`star-service.js:59-85` 同样如此。
- **影响**：用户可阅读邮件，却无法按可见主题／正文完整检索，total 也不能表达真实匹配集合。
- **最小修复**：保持静态加密，采用所属用户范围内有界解密搜索，或经单独隐私评估的索引方案；匹配、计数和分页统一。不能以全表无界解密或改存明文换功能。
- **正常验收**：三个邮件模式下，相同可见内容的查询语义一致；from／to／标签／日期／文件夹和星标组合仍工作，跨页不漏不重。

### M6. P1：站内直投跳过用户收件规则与通知／转发

- **证据**：`email-service.js:826,1080-1083` 的 local route 进入 `mail-local-delivery-service.js:112-181`，直接提交收件记录与 receipts，未调用外部入站 `email/email.js:201-228` 的规则及个人通知／转发任务链。
- **影响**：正常邮件仅因发送方在本站内，就不再按用户设定打标签、标已读、移动文件夹或通知转发。
- **最小修复**：共享收件规则与后续任务生成逻辑；保留内部邮件策略例外，不把外部拦截机械套到系统邮件。
- **保全／验收**：逐收件人 receipts、部分拒收、跨 BYO 附件复制和幂等恢复不退步；正常站内邮件得到预期规则结果和已开启的通知。

### M7. P2／正式分库前阻塞：欢迎信与公告仍混用数据域

`setting-service.js:878-881,1027-1030` 用默认 USER_DB ORM 查询 account；`email-service.js:1641,1793-1795` 用 MAIL_DB ORM 查询 user。冻结生产配置三绑定仍指同一 D1，因此不能报为当前所有环境缺表。正式物理分库前改为明确 userOrm／mailOrm 和两阶段查询，并在独立两库正常完成欢迎信、角色公告和新用户补发验收。**本次不必为了上线立即分库。**
